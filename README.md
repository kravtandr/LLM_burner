# LLM Burner

Локальный веб-тестер OpenAI-совместимых LLM endpoints: TPS, пропускная способность, задержки и история замеров. Два переключаемых режима — простой для быстрого теста и расширенный для исследования нагрузки.

## Запуск

Node.js **22.13+**.

```bash
npm install
npm run build
npm start
```

Откройте **http://127.0.0.1:4310**. Разработка: `npm run dev`, UI на **http://127.0.0.1:5173**.

```bash
PORT=4320 DATA_DIR=./my-data npm start
```

Сервер слушает только loopback. Это однопользовательский инструмент без аккаунтов и публичного доступа. HTTP-запросы к модели выполняются с этого компьютера. Одновременно выполняется один тест.

## Простой режим

- Base URL или полный URL Chat Completions, модель, необязательный API key; получение списка моделей через `/models`.
- System context, user prompt, параллельность, количество запросов, максимальный output и таймаут.
- Общий output throughput, end-to-end TPS запроса, TTFT, p95, request/s, прогресс и отдельные результаты.
- История с датой/временем, поиск, повтор параметров, сравнение 2–4 запусков, JSON/CSV результатов.
- Остановка отменяет активные запросы. Обновление вкладки не прерывает тест.
- Демо с синтетическим SSE без внешних запросов; маркируется в UI и экспорте.

## Расширенный режим

Тогл вверху сохраняет предпочтение. Запуск из простого режима использует только видимые базовые настройки; сохранённые расширенные параметры не применяются скрыто. Переключение вида текущего теста не меняет его нагрузку.

- **Прогрев:** отдельные запросы перед каждой ступенью; сохраняются, но исключаются из измерений.
- **Нагрузка:** постоянная параллельность либо заданный RPS с равномерными/Poisson интервалами. Предел одновременных запросов действует и в RPS-режиме; задержка относительно расписания записывается в `queueMs`. При насыщении фактический RPS может быть ниже заданного.
- **Разгон:** число разрешённых активных запросов растёт от 1 до заданной параллельности. В режиме RPS это разгон лимита параллельности, не самого RPS.
- **Длительность:** ограничивает время отправки новых запросов на каждой ступени; активные запросы завершаются в пределах своих таймаутов. Ступень заканчивается при достижении числа запросов или времени; итоговый прогресс может быть меньше 100% лимита запросов.
- **Sweep:** до 8 последовательных ступеней параллельности, отдельные метрики и кривая throughput. Количество запросов и прогрев задаются на каждую ступень. Остановка отменяет последующие ступени.
- **Набор запросов:** JSON-массив строк или файл; по кругу либо случайный выбор. Seed фиксирует выбор и Poisson-расписание, но не время сети/модели.
- **Кэш:** уникальный префикс user prompt; системный контекст остаётся прежним. Это изменяет запрос и не гарантирует отключение кэша сервера.
- **Sampling:** temperature, top_p, seed, опционально `continuous_usage_stats`.
- **SLO:** пределы TTFT, полной задержки, TPOT; request/token goodput и доля запросов в рамках всех пределов.
- **Статистика:** N, mean, min/max, population σ, p50/p90/p95/p99 для 16 распределений; ошибки по типам, причины завершения, reasoning/cache/prediction usage, покрытие данных.
- **Оценка стоимости:** явно заданные пользователем USD за миллион input/output токенов. Только успешные измеряемые запросы, без прогрева и ошибок; не счёт провайдера. Cache-тарифы отдельно не учитываются.
- Пресеты latency/throughput/sweep/RPS, импорт/экспорт конфигурации без ключа.

Ограничения: 1–128 одновременно, до 10 000 измеряемых запросов **на ступень**, до 1000 прогревочных на ступень, до 131 072 output токенов на запрос. Dataset: до 1000 строк, 100 000 символов на строку, 500 000 суммарно. Это ограничения клиента; сервер/модель могут иметь меньшие лимиты. Параллельность каждой ступени должна быть не выше её лимита запросов. Заданный лимит не гарантирует, что endpoint достигнет этой параллельности: короткие ответы, RPS, разгон и длительность влияют на фактическую нагрузку.

## Методика

Все времена измеряются монотонными клиентскими часами и включают сеть и overhead клиента. Измеряемое время — сумма длительностей измерительных фаз, включая ошибки, ожидание расписания и завершение активных запросов; прогрев исключён. Полное время с прогревом показано отдельно.

| Метрика | Расчёт |
| --- | --- |
| Output / input / total throughput | Соответствующие usage токены успешных запросов / измеряемое время |
| TPS запроса, end-to-end | `outputTokens / durationSeconds`; среднее по запросам с usage |
| Request/s | Успешные запросы / измеряемое время |
| TTFT | Начало HTTP → первый непустой content или reasoning delta |
| TTFO | Начало HTTP → первый непустой видимый content delta |
| TTST | Первый → второй чанк с генерацией; не доказанное время отдельного токена |
| Decode duration | Время последнего чанка с генерацией минус время первого; trailing usage не включён |
| TPOT | Decode duration / (output tokens − 1), только при ≥2 чанках и >1 токене |
| Decode TPS | `1000 / TPOT_ms` |
| Continuous usage | Если запрошен и валиден usage первого чанка, вместо 1 вычитается число его токенов; иначе обычная оценка. Метод записан в `tokenTimingMethod` |
| ICL | Интервалы между чанками с генерацией: средний и максимум внутри каждого запроса |
| Input / TTFT | Клиентская оценка prefill, включает очередь и сеть |
| Queue delay | Фактическое начало отправки минус плановое в RPS-режиме |
| Goodput | Успешные запросы, выполнившие **все** SLO, / измеряемое время |
| Good request fraction | Выполнившие SLO / все завершённые измеряемые запросы, включая ошибки и отмены |

Распределения строятся по успешным измеряемым запросам; перцентили — nearest rank, σ — population standard deviation. Распределение ICL относится к средним каждого запроса, а не к общей выборке всех межчанковых интервалов. Также доступны распределения input/output lengths, bytes received и числа чанков. График во времени показывает накопленный output throughput по завершённым запросам, не мгновенную скорость прихода токенов.

Токены берутся только из API usage. Чанки не считаются токенами, локальная токенизация не подменяет usage. Если usage неполон, соответствующий общий throughput и стоимость недоступны; счётчики известных токенов сопровождаются покрытием. Optional reasoning/cache/prediction суммы доступны только при полном покрытии соответствующего поля успешных запросов. Prediction usage — не метрики внутренних speculative decoding steps.

При неизвестном значении включённой SLO-метрики запрос попадает в «неизвестно» и не включается в goodput. Без заданных SLO goodput недоступен. В sweep общая сводка смешивает ступени; сравнивайте также таблицу отдельных ступеней.

`continuous_usage_stats` — необязательное расширение сервера, по умолчанию выключено. Не все OpenAI-совместимые endpoints его принимают. Даже с ним chunk timing не превращается в отдельные token timestamps. `completion_tokens` может включать reasoning согласно учёту провайдера.

Для cache-busting к user prompt добавляется `Benchmark request: <run-id>:<stage-index>:<phase>:<request-index>\n\n`. Полная исходная конфигурация, seed и фаза сохраняются, текст сгенерированного ответа — нет. Автоматических повторов нет.

## Источники и границы

Метрики и сценарии адаптированы по публичной документации **NVIDIA AIPerf**, GuideLLM и EvalScope; удобство сравнения истории — с учётом llm-api-bench. Реализация самостоятельная, сторонний код не скопирован. [Точные версии источников и соответствие функций](docs/upstream-sources.md).

Поддерживаются потоковые текстовые Chat Completions. Не реализованы Responses API, нативные Anthropic/Ollama API, non-streaming, мультимодальность, GPU/DCGM/Prometheus-телеметрия, распределённые генераторы, tokenizer-based synthetic lengths, replay traces и автоматический поиск максимума. Это не полный порт AIPerf. Отсутствующие данные отображаются «—».

## Хранение и секреты

SQLite: `data/burner.sqlite`. Сохраняются контекст, endpoint, настройки, дата/время и метрики. API-ключ живёт в памяти формы/активного теста, не сохраняется в БД/localStorage/экспорте. При импорте ключ отбрасывается; после обновления страницы или повтора параметров введите его заново. Тела ошибок провайдера не сохраняются.

Результат запроса и сводка checkpoint сохраняются одной транзакцией. После аварийного завершения незавершённые тесты помечаются «Прерван», метрики пересчитываются по сохранённым строкам. Неоконченные запросы не возобновляются. Даты хранятся в UTC, показываются в часовом поясе браузера. Для backup остановите сервер и скопируйте `data`.

## Проверки

```bash
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Backend tests покрывают HTTP/SSE, формулы, прогрев, RPS/seed/ramp/sweep, отмену, SQLite recovery, API, секреты и экспорт. Playwright использует отдельный сервер 4319 и базу `test-results/e2e-data`: запуск/история/refresh, мобильная вёрстка, оба режима, сравнение, импорт/экспорт и реальные HTTP-запросы к локальному fixture. Внешняя модель без предоставленных URL/model/credentials не проверялась.

Структура: `server/transport.mjs` — SSE/тайминги, `metrics.mjs` — формулы, `runner.mjs` и `scheduling.mjs` — нагрузка, `store.mjs` — SQLite, `app.mjs` — API, `src/` — UI, `shared/settings.mjs` — общие defaults и фильтрация настроек.
